## 1. עץ ניווט — מה מתווסף (מודגש) למבנה הקיים

```
נהג — Menu (DRIVER_ITEMS)
└── מסמכים חתומים  (DriverSignedDocuments — קיים)
    ├── שורת מסמך [pending]  → **חדש**: מסך "פרטי מסמך + חתימה" (DriverDocumentSign)
    │                            ├── תצוגת PDF (Linking.openURL, כמו היום)
    │                            └── signature pad → אישור → סטטוס מתעדכן ל"נחתם" מיידית, נשאר במסך
    └── שורת מסמך [signed]   → פתיחה לצפייה בלבד (כמו היום — ללא שינוי, ללא כפתור חתימה)

אדמין — Menu (ADMIN_ITEMS)
├── מסמכים חתומים  (DocumentTemplatesScreen — קיים, ללא שינוי היקפי)
│   └── תבנית בודדת (DocumentTemplateDetailScreen — קיים)
│       └── **חדש**: שלב שלישי חובה בטופס "הוספת מסמך" — סימון מיקום חתימה (FR1)
│           (לא עמודת סטטוס/מונה חתימות — נאסר במפורש ב-FR5)
│
└── ניהול נהגים → כרטיס נהג (DriverDetailScreen — קיים)
    └── תפריט שטוח (MENU) + **שורה חדשה: "מסמכים חתומים"**
        → **חדש**: מסך DriverSignedDocumentsAdmin (route מוצע: `DriverSignedDocumentsAdmin: { driverId }`)
            ├── רשימת כל השליחות לנהג הזה (מכל התבניות), עם סטטוס
            ├── שורת [pending] → הרחבה בתוך השורה עצמה: רק סטטוס, אין תצוגה/הורדה
            └── שורת [signed]  → תצוגת הטופס החתום המלא + תאריך חתימה + כפתור הורדה
```

**חשוב (FR5 — לא להתבלבל):** `DriverSignedDocuments` (הנהג) ו-`DriverSignedDocumentsAdmin` (האדמין, בפרופיל נהג ספציפי) הם שני מסכים נפרדים לגמרי — אותו שם תצוגתי ("מסמכים חתומים"), אותה משפחת נתונים (`document_sends`), הרשאות/query שונות (`driver_id = auth.uid()` מול `driver_id = <driverId מהניווט>` תחת הרשאת `can_manage_company`). מומלץ למתן להימנע מ-route/component משותף בין שני אלה מעבר לרכיבי UI גנריים (Card, סטטוס pill) — הלוגיקה והרשאות שונות.

## 2. User Flow — חתימת נהג (FR2/FR3/FR7)

```
[מסמכים חתומים - רשימה]
  → לחיצה על שורת מסמך pending
[מסך פרטי מסמך]
  displays: שם מסמך, תאריך שליחה, כפתור "צפייה במסמך (PDF)" (פותח חיצונית — כמו היום),
            כפתור בולט "חתימה על המסמך"
  → לחיצה "חתימה על המסמך"
[מסך/מודאל חתימה — קנבס ריק]
  ├── מנסה "אשר וחתום" על קנבס ריק → שגיאה בעברית, נשאר במסך (FR2 קבלה)
  ├── מצייר קו → כפתור "נקה" מאופשר → לחיצה מרוקנת, חוזר למצב קנבס ריק
  ├── מצייר קו תקין → לחיצה "אשר וחתום"
  │     → מצב טעינה (compose+upload בשרת, ~<3 שניות לפי קבלה FR3)
  │     → הצלחה: המסך חוזר למצב צפייה, סטטוס מוצג כ"נחתם" מיידית, אין יותר כפתור חתימה
  │     → כשל (רשת/שרת): הודעת שגיאה בעברית, הקנבס/הטיוטה **לא** נשמרים (FR7),
  │        הנהג יכול לנסות שוב מיד (המסמך עדיין pending)
  └── יציאה מהמסך/מהאפליקציה לפני "אשר וחתום" (כל שלב) → שום דבר לא נשמר,
        חזרה לרשימה מציגה את המסמך עדיין כ"ממתין" (FR7, סגור סופית ע"י דור)
```

### Edge cases שטופלו במפורש בעיצוב
| מקרה | התנהגות מעוצבת |
|---|---|
| קנבס ריק + לחיצה על אישור | חסימה + הודעת שגיאה בעברית, המודאל/מסך נשאר פתוח (FR2 קבלה) |
| יציאה באמצע ציור (back/הום/סגירת אפליקציה) | ללא שמירה, סטטוס נשאר pending (FR7 — סגור, לא שאלה פתוחה) |
| מסמך כבר signed (למשל נחתם ממכשיר אחר בינתיים / collapse) | אין כפתור "חתימה על המסמך" כלל — צפייה בלבד (FR2 קבלה, תואם-קדימה) |
| כשל ברשת בזמן "אשר וחתום" | הודעת שגיאה בעברית ברורה, לא "תקוע" במצב טעינה אינסופי, ניתן לנסות שוב |
| collapse (FR4) — נהג חותם על עותק אחד מתוך כמה pending של אותה תבנית | לאחר אישור, הרשימה (מסך הרשימה שממנו הגיע) מציגה **את כל** העותקים של אותה תבנית כ"נחתם" — לא רק את זה שנחתם בפועל. אין הבחנה ויזואלית "זה נחתם ישירות / זה קרס" — לפי ה-PRD זו אותה חתימה בפועל |
| מסמך רב-עמודים, אזור חתימה בעמוד שאינו הראשון | בתצוגת "פרטי מסמך", אין צורך להציג את העמוד הספציפי מראש (אין רינדור PDF פנימי, ר' `research.md`) — הנהג פותח את ה-PDF המלא חיצונית ורואה את כל העמודים; הקנבס עצמו הוא רכיב נפרד, לא "ציור על גבי" תוכן ה-PDF |

## 3. User Flow — סימון מיקום חתימה בעת יצירת תבנית (FR1, אצל האדמין)

```
[DocumentTemplatesScreen] → "הוספת מסמך"
[שלב 1] שם המסמך  (קיים)
[שלב 2] בחירת קובץ PDF  (קיים)
[שלב 3 — חדש] סימון מיקום חתימה — חובה, לא ניתן לשמור בלעדיו (FR1 קבלה)
  ├── בחירת עמוד (1 עד 4, לפי הגבלת PDF הקיימת)
  ├── תרשים עמוד סכמטי (לא רינדור PDF אמיתי — ר' סעיף 4 להלן להסבר ולחלופות)
  │     → גרירה/שינוי גודל של תיבת חתימה יחידה על גבי התרשים
  ├── קישור "פתח את ה-PDF לצפייה" (Linking.openURL, אותו מנגנון קיים) — כדי שהאדמין
  │     יוכל לוודא מול התוכן האמיתי איפה בעמוד באמת כדאי למקם את התיבה
  └── שמירה → מוודא שנבחר עמוד + תיבה, אחרת חוסם עם שגיאה
[שמירה מוצלחת] → ניווט למסך פרטי תבנית (כמו היום), מיקום החתימה כעת קבוע לצמיתות (תבנית immutable)
```

### Edge cases
| מקרה | התנהגות מעוצבת |
|---|---|
| ניסיון לשמור תבנית בלי לסמן תיבה | חסימה + שגיאה, כמו שדה "שם" ריק היום |
| תבנית ישנה (לפני מיגרציה 38) בלי מיקום חתימה כלל | לא ניתנת לעריכה (immutable ממילא) — אין UI "השלם מיקום בדיעבד"; אם רוצים להפוך אותה לחתימה-אפשרית, יוצרים תבנית חדשה ושולחים מחדש (בדיוק כפי שכתוב בהערת המיגרציה) |
| שינוי גודל תיבה כך שחורגת מגבולות העמוד | נחסם ב-UI (drag מוגבל לגבולות התרשים) — תואם את ה-CHECK constraint בסכימה (`x+width<=1`, `y+height<=1`) |

## 4. החלטת UX/טכנית ל-FR1 — איך בפועל מסמנים מיקום (סוגיה שה-PRD האציל לירון/מתן במפורש)

**זו לא רק החלטת UI — יש לה עלות פיתוח ממשית**, ולכן שלוש חלופות מוצגות עם trade-offs, לא פתרון יחיד:

**אופציה A — גרירת תיבה על גבי רינדור אמיתי של עמוד ה-PDF (thumbnail).**
- יתרון UX: הכי מדויק ואינטואיטיבי — האדמין רואה בדיוק את התוכן שמתחת לתיבה.
- חיסרון: דורש ספריית רינדור PDF-לתמונה בקוד (לא קיימת היום, ר' `research.md`) — עלות פיתוח משמעותית, תלות חדשה, וזמן בנייה ארוך משמעותית יותר.

**אופציה B — תרשים סכמטי בלבד (מלבן ריק ביחס-רוחב A4), בלי קישור לצפייה בתוכן האמיתי.**
- יתרון: אפס תלות חדשה, הכי מהיר לבנייה.
- חיסרון UX: האדמין "מנחש" מיקום יחסית לתוכן שהוא לא רואה במסך הזה — סיכון לטעויות מיקום (חתימה שמכסה טקסט, או ממוקמת רחוק מדי מהמקום ההגיוני בטופס).

**אופציה C — היברידי (מומלץ על ידי, בכפוף לאישור טכני של מתן): תרשים סכמטי + קישור מפורש "פתח PDF לצפייה" לצד התרשים (אותו מנגנון `Linking.openURL`/signed URL שכבר קיים היום ב-`getTemplateFileUrl`).**
- יתרון: אין תלות פיתוח חדשה (0 ספריות חדשות), האדמין בכל זאת יכול לוודא מול המסמך האמיתי (בטאב/אפליקציה חיצונית) לפני/תוך כדי סימון התיבה בתרשים, זמן בנייה קרוב לאופציה B.
- חיסרון: פחות נוח מ-A (מעבר הקשר בין שני מקומות — התרשים והצפייה החיצונית), עדיין תלוי בזיכרון/דיוק האדמין.

**המלצתי (UX+UI, לא רק שיקול טכני): אופציה C** — מאזנת בין דיוק סביר לעלות פיתוח נמוכה, ותואמת את הדפוס הקיים כבר באפליקציה (צפייה חיצונית ב-PDF). זו **הנחת עבודה/המלצה שדורשת אישור טכני של מתן** לפני שהיא הופכת לסופית — אם מתן מעריך שרינדור PDF (אופציה A) זול יותר מכפי שאני מניחה, זו בחירה טכנית לגיטימית לשדרג אליה. הוויירפריים/פרוטוטייפ למטה בנויים לפי אופציה C.

## 5. חיבור למדד עסקי

- **Adoption/Reach של החתימה בפועל**: `signed_at` שנוסף במיגרציה 38 מאפשר כעת למדוד "זמן מקבלת מסמך ועד חתימה" (PRD שלב 1, סעיף 8, מדד עתידי) — לא נבנה analytics UI כאן, אך זרימת החתימה שעוצבה כאן (מהירה, ללא חיכוך מיותר — קנבס אחד, כפתור אחד) היא מה שמאפשר את זמן ה-Time-to-Sign הקצר שה-PRD שואף אליו ("מהיר, מהשטח").
